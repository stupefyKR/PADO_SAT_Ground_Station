# 가상 위성 비콘·명령·저장 TM

## 동작

가상 위성은 TLE 기반 truth 궤도에서 5초마다 전력·온도, −X Nadir 자세,
GNSS TM을 만들고 최대 24시간 동안 자체 SQLite 볼륨에 저장한다.
교신 여부와 관계없이 표본 생성은 계속된다. 센서값은 연속적인 함수로 변하며,
GNSS와 자세는 같은 시각의 궤도에서 계산한다.

연세대 UHF PASS에서는 기본 10초 주기의 정상 HK 비콘 묶음을 수신한다.
ROS에서 **TC 준비 · 예약 → 가상 위성 저장 TM 수신 → 저장 TM 요청**을 누르면
`hk_dump`가 가상 위성에 전달된다. 위성은 `COMMAND_RESULT`로 요청을 수락한 뒤
그 순간까지 저장돼 있던 TM을 원래 측정 시각 순서대로 내린다.

```text
가상 위성: 표본 생성 → 저장 ──────────────→ TC 요청 시 저장분 전송
                         비콘 ↓                 TM ↓
ROS: 비콘 확인 → 저장 TM 요청 → sim-ground → 가상 위성 dispatcher
              ← 요청 수락 ACK ←─────────────┘
              ← 센서·자세 그래프 / GNSS → FDS 예측
```

ACK는 **요청 수락**을 의미한다. 지상국의 모든 TM 수신 완료를 뜻하지 않는다.
요청 이후 새로 생성된 TM은 다음 요청까지 남긴다. LOS·접속 종료·컨테이너
재시작 시 전송 허가는 끝나며, 남은 자료는 다시 요청해야 한다. 불확실한
TC를 지상국에서 자동 재전송하지 않는다.

## 사용하는 패킷

`interfaces/pado_packets/draft_v0.json`의 애플리케이션 PDU를 사용한다.
현재 상태를 담는 `MODE_BEACON`·`BEACON_INFO` 시험 PDU를 추가했으며 실제 RF 프레임은 구현하지 않는다.

| 방향 | 이름 | 역할 |
| --- | --- | --- |
| 위성 → 지상국 | `BEACON_CORE` | 비콘 순번·주기·모드·시험 저장소 사용률 등 |
| 위성 → 지상국 | `MODE_BEACON`, `BEACON_INFO` | 장비별 현재 상태·식별 정보 |
| 지상국 → 위성 | `hk_dump` | 저장된 TM 전송 요청 |
| 위성 → 지상국 | `COMMAND_RESULT` | TC ID·순번과 요청 수락 또는 거절 |
| 위성 → 지상국 | 장비별 계측 TM 13계열·`FULL_HK_CHUNK` | 저장된 원본 계측·자세·GNSS·전체 HK |

`hk_dump`의 `start_utc_ms=0`, `end_utc_ms=0`은 요청 순간의 저장분 전체를
뜻하는 시험 규칙이다. 두 값을 지정하면 과거 24시간 이내의 엄격히 증가하는
UTC 구간을 선택한다. 이미 전송해 저장소에서 지운 자료는 다시 만들지 않는다.
ROS의 즉시 요청 버튼은 전체 저장분을 요청한다.

| 거절 이유 값 | 의미 |
| ---: | --- |
| 1 | 처리기 미등록 |
| 2 | 위성 내부 실행 시각 예약 미지원 |
| 3 | 중복 요청 또는 중복 방지 저장소 한도 |
| 4 | 요청 시각 만료·미래 시각 |
| 5 | 명령 인자 오류 |
| 6 | 처리기 실행 오류 |

## 기능 추가 위치

`services/sim_sat/dispatcher.py`의 `TcDispatcher`가 명령 이름과 처리기를 연결한다.
현재 `hk_dump`는 저장분 전송 동작을 만들며, 기존 조회 명령은 수락 응답만
돌려준다. 조회 응답에 실제 하위 시스템 자료를 추가하려면 별도의 처리 동작을
구현해야 한다.

1. 시험 카탈로그에 명령 ID·인자를 정의한다. 기존 명령이면 그대로 사용한다.
2. `(decoded_command, CommandContext) → CommandAction` 처리기를 작성하고
   `dispatcher.register(name, handler)`로 명시적으로 등록한다.
3. 새로운 동작이 필요하면 `CommandAction`과 `SatelliteSession`의 실행 부분을
   함께 확장한다. 처리기는 네트워크 전송을 직접 수행하지 않는다.
4. 지상국 송신 허용 목록·인자 검증·화면을 필요한 범위만 추가하고, 잘못된
   인자·중복 TC·LOS·재시작 시험을 추가한다.

CRC·PDU 길이·시험 표시·TC 종류 검사는 공통 코덱에서 수행한다. 위성은
최근 요청의 시각·순번을 SQLite에 저장해 재시작 직후의 재실행도 막는다.
명령 이름을 받아 임의의 Python 함수나 셸 명령을 실행하는 경로는 없다.

## 지상국 연결과 확인

웹 요청은 기존 로그인·역할·CSRF 검사를 거친다. ROS의 별도 요청 기록은
`QUEUED → SENDING → ACKED / REJECTED / TIMEOUT / SEND_FAILED` 상태를 가진다.
30초를 넘겨 대기한 요청은 `MISSED`, 송신 중 재시작된 요청은 `UNKNOWN`으로 남는다.
비콘은 `test_beacon.json`, 센서·자세 이력은 `test_tm_snapshot.json`으로
분리한다. 비콘을 받는 것만으로 센서값이 최신 상태로 바뀌지 않는다.

```sh
cd ~/pado-gs
git pull --ff-only origin feat/fds-core
./pado-gs.sh start
docker logs --tail=30 pado-stage9-local-sim-satellite-1
```

교신 중 비콘 상태를 확인한 뒤 ROS에서 요청한다. 요청 수락 로그와 TM 수신에
따른 그래프 갱신을 확인한다. PASS 밖의 요청은 송신하지 못하며, 다음 PASS에서
사용자가 다시 요청한다. N11에는 수신 시각 기준 120초 이내의 신선한 GNSS만
전달하므로 오래된 저장분만 받았을 때 FDS는 해당 자료로 갱신되지 않는다.

외부에 게시하는 포트는 기존 DGS 진입점 하나다. ROS와 `sim-ground`는 비공개
Unix socket, `sim-ground`와 가상 위성은 기존 Docker 내부 TCP 9200을 사용한다.
비콘·TC·TM 모두 양쪽의 truth PASS 검사 대상이며, 실제 RF·안테나·운용
명령 송출 경로와는 분리된다.

위성 저장 한도 초과 시 가장 오래된 완전한 표본 묶음을 지우고 로그를 남긴다.
지상국은 모든 수신 원문·파싱 값을 SQLite에 저장한 뒤 개별 수신 확인을 보낸다.
위성은 확인된 PDU만 삭제하며, 확인되지 않은 저장분은 다음 요청에 다시 보낸다.
ROS 그래프는 최근 1시간 이력, 수신 TM 탭은 영속 아카이브를 사용한다.
장비 항목·원문 조회·저장 상한은 [시뮬레이션 TM 안내](SIM_TELEMETRY_PROFILE.md)에 정리했다.

## MPS 예약으로 자동 수신

MPS에서 미래의 연세대 UHF PASS를 선택하고 TC를 실행할 순서대로 쌓는다.
예를 들어 `mm_get_mode` → `eps_get_hk` → `hk_dump` 순서다. `hk_dump`의
두 시각을 `0`으로 두면 요청 순간의 전체 저장분을 받는다.

명령마다 시각을 입력하지 않는다. 시퀀스 전체에 **AOS 몇 초 후**를 한 번
지정하며, 기본값은 10초다. 화면에는 `AOS 10초 후`와 그에 해당하는 UTC
시작 시각을 함께 표시한다. 이 값은 현재 시각으로부터의 지연이 아니다.

시퀀스를 저장한 뒤 `ROS 시험 초안으로 전달`을 누른다. ROS의 `TC 준비 · 예약`에서
전달된 시퀀스의 순서·공통 시작 시각을 확인하고 `시퀀스 전체 예약`을 한 번 누른다.
전체 TC를 하나의 트랜잭션으로 예약하므로 중간 일부만 예약되지 않는다.
MPS 저장이나 ROS 전달만으로는 명령이 실행되지 않는다.

예약 시각부터 첫 TC를 보내고, 앞선 TC의 ACK를 확인한 뒤 다음 TC를 순서대로
보낸다. 공통 UTC는 시퀀스 **시작 시각**이며 각 TC의 실제 송신·응답 시각은
통신 지연에 따라 달라진다. 시작이 30초 넘게 늦으면 전송하지 않으며, 정상
시작한 시퀀스의 후속 명령에는 같은 30초 제한을 중복 적용하지 않는다.
LOS 이후에는 후속 TC를 보내지 않는다. 거절·시간 초과·송신 실패·결과 불명 시
나머지를 중단하고, 불확실한 송신을 자동 재시도하지 않는다.

시퀀스 취소는 아직 보내지 않은 명령에 적용된다. 이미 송신한 명령을 되돌리거나
응답을 받기 전에 다음 명령을 보내는 기능은 아니다. 기존 개별 시각 초안은
자료를 보존하며, 서로 다른 오프셋을 가진 초안은 MPS에서 공통 시작 시각으로
다시 저장·전달한 뒤 전체 예약할 수 있다.

2026-10-28 Linux의 실제 HTTP·Unix 소켓 통합 시험에서는 AOS + 10초의 공통
시작으로 `mm_get_mode` → `eps_get_hk` → `hk_dump` 3개 명령을 예약했다.
저장한 순서대로 송신되고 각 명령의 ACK가 일치해 3건 모두 ACKED였다.
시작 전 TC와 `hk_dump` 전 저장 TM 송신은 없었으며, 이후 저장 TM 285개,
RAW·파싱 값, 전체 HK와 센서 20개 이력을 확인했다. LOS 이후 송신 차단도
유지됐다. 이 시험은 합성 PASS를 사용하며 VM 배포·실제 RF 판정은 포함하지 않는다.

2026-10-27 WSL Ubuntu의 실제 HTTP·Unix socket·양방향 소켓 통합 시험 결과:

| 확인 항목 | 결과 |
| --- | --- |
| 웹 API의 PASS 조회 → `hk_dump` 저장 → ROS 전달·예약 | 통과, 리비전 1 |
| 예약 시각 전 송신·저장 TM 수신 | 없음 |
| AOS + 10초의 자동 TC 송신 | 1회, 예약 시각으로부터 약 0.53초 뒤 위성 수신 |
| 위성 응답 | `COMMAND_RESULT`, ID 4116, 수락 |
| 저장 TM 수신·ROS 게시 | PDU 48개, 전압·온도 각 16개 표본과 자세 |
| GNSS N11 게시 | 파일 쌍 1개 |
| MPS의 ROS 응답·상태 피드백 | ACK 표시, `CURRENT` |
| AOS 이전·LOS 이후 TC | 차단 |
| 요청 이후 새 TM | 6개 PDU 보관, 자동 전송 없음 |

재현은 기존 스택과 별도의 시험 디렉터리에서 수행한다. Linux에서 아래 명령을
실행하면 약 40초 뒤 `report.json`을 남긴다. 출력 디렉터리는 새 이름을 사용한다.

```sh
python3 -m tests.run_scheduled_dump_smoke --output out/scheduled-dump-check-1
```

이 시험은 명령 처리·예약 시계·저장소·파서·게시 코드를 실제로 실행한다.
FDS 일정 공급 함수는 짧은 합성 PASS로 대체하고, 격리된 시험 계정의 비밀번호
해시를 사용한다. 실제 FDS 기하 계산·브라우저 렌더링·Docker 격리·VM 배포·RF
수신 성공을 판정하는 시험은 아니다. Linux CI의 전체 Python 시험에 포함되며,
별도의 Docker 시험은 예약 `hk_dump`의 ACK 뒤 최신 센서 TM 게시까지 확인한다.

확장된 전체 장비 TM 시험에서는 저장 PDU **256개**와 비콘·ACK를 합친 **263개**의
아카이브 기록, 20개 센서 각 16개 표본, 전체 HK 재조립, RAW·파싱 값 일치와
지상국 영속 저장 receipt 완료를 확인했다. 새로 생성된 39개 PDU는 다음 요청까지
남았다. 동일한 Linux 합성 PASS 시험이며 실제 VM·RF 판정은 포함하지 않는다.
