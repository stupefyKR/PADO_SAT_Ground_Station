## 1. 방향 전환 배경

### 1.1 기존 계획의 문제

기존 계획은 국가정보원의 국가 망 보안체계(N²SF)를 과제의 뼈대로 삼았다. 검토 결과 다음 이유로 대학 지상국에는 맞지 않다고 판단하였다.

- **적용 대상이 아니다.** N²SF는 국가·공공기관의 망분리 정책을 대체하는 체계이며, 사립대학 연구실 지상국은 적용 대상이 아니다.
- **등급 정의가 맞지 않는다.** N²SF의 C(기밀)는 안보·국방·외교·수사 등의 정보를 뜻한다. 대학 큐브위성 TC는 *임무 영향이 큰* 정보이지 *기밀*이 아니다. 이 표기는 항우연과 협의할 때 불필요한 오해를 만들 수 있다.
- **설계에 더해 주는 것이 적다.** 실제 통제(구역 분리, 기본 거부, 역할별 권한, 2인 승인)는 NIST IR 8401 등 일반적인 지상국 보안 기준에서 그대로 나오는 내용이다.
- **실제 기준은 연결 상대가 정한다.** 대학 지상국의 보안 수준을 결정하는 것은 우리가 고른 프레임워크가 아니라, 항우연이 외부 연동을 허용할 때 요구하는 조건이다.

### 1.2 유지하는 문제의식

N²SF를 빼더라도 보안의 중요도는 그대로다. 항우연 지상국과의 **직접 연결점**이 존재하고, 우리가 개발한 지상국을 항우연에 연결해 달라고 요청할 때 **보안 대책에 대한 논의는 반드시 필요**하다. 따라서 본 과제는 다음 두 가지를 목표로 다시 구성한다.

1. 항우연에 연동을 요청할 때 제시할 수 있는 **구체적이고 검증 가능한 보안 대책**을 갖춘다.
2. 학생 중심 조직이 **실제로 구축하고 유지할 수 있는 규모**로 설계한다.

### 1.3 설계 원칙

| 원칙 | 내용 |
|---|---|
| 위험 기반 | 프레임워크 준수가 아니라 실제 위험(명령 경로 탈취, 연동 구간 침해, 데이터 손실)에서 출발한다. |
| 명령 경로 우선 | 위성으로 향하는 TC 경로의 무결성을 가장 먼저 보호한다. |
| 단일 접점 | 외부와의 모든 통신은 DGS만 수행한다. 그 외 서브시스템은 외부망과 완전히 분리한다. |
| 단순성 | 검증·필터링 로직은 허용 목록 대조처럼 단순한 규칙으로 만든다. 복잡한 규칙은 설정 오류의 원인이 된다. |
| 유지 가능성 | 인원이 바뀌어도 문서와 체크리스트만으로 운용·점검할 수 있어야 한다. |
| 기록과 복구 | 모든 TC는 사후에 "누가, 언제, 왜, 무엇을" 보냈는지 재구성할 수 있어야 하며, 어떤 장애에서도 복구할 수 있어야 한다. |

### 1.4 참고 기준

N²SF는 뼈대에서 제외하되, 항우연이 요구할 경우를 대비해 **부록의 통제 항목 대응표**로만 유지한다.

- NIST IR 8401, Satellite Ground Segment: Applying the Cybersecurity Framework to Satellite Command and Control (주 기준)
- CCSDS 350.1-G (우주 임무 보안 위협), CCSDS SLE 관련 권고(RAF/RCF/FCLTU)
- NIST SP 800-41 (방화벽 정책), NIST SP 800-207 (제로트러스트 원칙 차용)
- 국가정보원 N²SF 보안가이드라인 1.0 (참조·대응표용)

※ 표준 명칭과 번호는 최종 문서에 넣기 전에 원문으로 확인한다.

## 3. [0] 항우연·연세대 연동 모델과 협의 요구사항

### 3.1 기본 가정

항우연·연세대와의 연동 방식은 아직 확정되지 않았다. 본 과제는 다음을 **기본 가정**으로 두고 설계하며, 협의 결과에 따라 3.5절의 대안으로 조정한다.

- 경희대 DGS와 항우연 지상국은 **IPsec 사이트 간 VPN**으로 연결한다.
- 연결 양 끝은 고정 주소이며, VPN은 연동 전용 장비(DGS 연동 게이트웨이)에서만 종단한다.
- 안테나 운용(추적, 변복조, RF 송수신)은 항우연이 수행하고, 경희대는 TC 생성과 TM 처리를 담당한다.
- 연세대 UHF 백업 지상국도 같은 방식으로 연결한다고 가정한다.

### 3.2 연결 방식 후보

| 방식 | 내용 | 장점 | 단점 | 판단 |
|---|---|---|---|---|
| A. IPsec 사이트 간 VPN | 양 기관 경계 장비 사이 암호화 터널 | 표준적, 양측 장비로 구현 가능, 주소 고정 용이 | 장비·설정 협의 필요, 학교 정보처 협조 필요 | **기본안** |
| B. 전용회선 | 물리적 전용 회선 | 인터넷과 완전 분리 | 비용이 크고 개설 기간이 김 | 장기 운용 시 검토 |
| C. 클라이언트 VPN | 운용 단말이 항우연 VPN에 개별 접속 | 빠르게 시작 가능 | 단말 관리 부담, 운용 단말이 외부와 직접 연결됨 → 단일 접점 원칙 위반 | 비권장 |
| D. 현장 운용 | 운용자가 항우연에 방문해 항우연 단말로 운용 | 네트워크 연동 불필요 | 매 패스 이동 불가, 상시 운용 어려움 | LEOP 등 한시적 대안 |
| E. 오프라인 파일 교환 | 패스 후 파일 단위 전달 | 실시간 연결 없음 | 실시간 TC 불가 | TM 사후 전달 등 보조 수단 |

### 3.3 데이터 교환 단위 후보

데이터 교환 단위는 **항우연이 어디까지 처리하고, 어디부터 우리가 처리하는가**의 경계다. 이 경계에 따라 보안 책임과 HMAC 적용 가능성이 달라진다.

#### Downlink (위성 → 항우연 → 경희대)

| 단위 | 항우연 처리 범위 | 경희대 처리 범위 | 대역폭 | 평가 |
|---|---|---|---|---|
| D1. RF/IF IQ 샘플 | 수신·디지털화까지 | 복조·동기·디코딩 전부 | 매우 큼 | 비권장. VPN 대역폭 부담이 크고 SDR 신호처리를 우리가 맡아야 함 |
| D2. 복조 비트스트림 | 복조까지 | 프레임 동기·디코딩 | 큼 | 비권장. 표준 인터페이스가 드묾 |
| **D3. 전송 프레임** (CCSDS TM Transfer Frame / AX.25 프레임) | 복조·프레임 동기·채널 디코딩 | 프레임 해석·패킷 추출 | 작음 | **권장**. CCSDS SLE RAF/RCF가 이 단위를 정의함. 항우연은 우리 패킷 구조를 몰라도 됨 |
| D4. 원시 패킷 (Space Packet 등) | 프레임 해석까지 | 패킷 해석 | 작음 | 가능하나 항우연이 우리 프레임 구조를 알아야 함 |
| D5. 파일·처리 산출물 | 전부 | 사후 분석 | - | 실시간 운용 불가, 보조 수단 |

Downlink 프레임에는 **수신 메타데이터**(지상 수신 시각, 수신 품질, 안테나 ID, 패스 ID)를 함께 붙이도록 요청한다. 로그·사후 분석의 기준이 된다.

#### Uplink (경희대 → 항우연 → 위성)

| 단위 | 경희대 처리 범위 | 항우연 처리 범위 | HMAC 종단성 | 평가 |
|---|---|---|---|---|
| **U1. 완성된 TC 프레임/CLTU** | TC 생성·HMAC 부착·프레임 구성 | 변조·RF 송출만 | **종단 간 유지** (항우연은 투명 중계) | **권장**. CCSDS SLE FCLTU가 이 단위를 정의함 |
| U2. TC 패킷 | TC 생성·HMAC 부착 | 프레임 구성·송출 | 패킷에 HMAC이 있으면 유지 | 가능. 항우연이 우리 프레임 규격을 구현해야 함 |
| U3. TC 요청 문서 | 명령 목록·시각을 문서로 요청 | TC 생성·송출 | **불가**. HMAC 키를 항우연에 넘겨야 함 | 비권장. 요청 문서 서명이 별도로 필요 (6.3절) |

**권장 조합: Downlink D3 + Uplink U1.** 항우연은 프레임을 그대로 주고받는 *투명 중계* 역할만 하고, HMAC 키와 명령 내용은 경희대 안에만 머문다. 항우연 입장에서도 우리 위성의 명령 체계를 알 필요가 없어 책임 범위가 명확해진다.

#### 별도 채널 데이터

TM/TC 외에 다음 데이터는 프레임 스트림과 분리된 **파일 교환 채널**(예: SFTP)로 주고받는다.

- 경희대 → 항우연: Antenna Pointing File(또는 궤도 요소), 패스 예약 요청
- 항우연 → 경희대: 패스 확정 일정, 패스 결과 보고, 안테나 상태

## 4. [1] 위성 TC 인증: 트랜시버 HMAC

### 4.1 결정 사항

위성 TC 인증은 **COTS 트랜시버가 제공하는 HMAC 기반 인증**을 사용한다. 지상국 네트워크 보안과 독립된 *마지막 방어선*이다. RF 송신 능력을 가진 제3자가 지상국을 거치지 않고 위성에 명령을 보내는 경로를 막는다.

### 4.2 적용 시 확인해야 할 사항

COTS 구현마다 HMAC의 강도와 기능이 다르므로 다음을 위성 개발팀과 함께 확인한다.

| 확인 항목 | 이유 | 미충족 시 보완 |
|---|---|---|
| 해시 알고리즘과 HMAC 길이 | 일부 구현은 HMAC 값을 짧게 잘라 사용함 | 위험 TC에 대해 추가 확인 절차 |
| **재전송(replay) 방지** 여부 | HMAC만으로는 정상 TC를 녹음해 다시 보내는 공격을 막지 못함. 순번·타임스탬프가 HMAC 범위에 포함되어야 함 | 위성 SW에서 명령 순번 검사 추가 요청 |
| HMAC 적용 범위 | 헤더 포함 여부, 적용 계층(패킷/프레임) | 범위에 맞춰 3.3절 교환 단위 재확인 |
| 키 변경 방법 | 키 유출 시 궤도상에서 교체 가능한지 | 불가하면 키 보관 통제를 더 강화 |
| HMAC 실패 시 위성 동작 | 무시인지, 카운트·보고하는지 | 실패 카운트를 TM으로 받아 공격 탐지에 사용 |
| 인증 비활성화 명령 존재 여부 | 비활성화 명령 자체가 최고 위험 TC | 해당 명령은 2인 승인 + 별도 절차 |

### 4.3 HMAC 키 관리

HMAC 키는 **위성 명령 권한 그 자체**다. 키를 잃으면 위성을 제어할 수 없고, 유출되면 누구나 위성을 제어할 수 있다.

- **보관 위치**: HMAC 계산은 ROS 내부(또는 ROS에 연결된 서명 모듈)에서만 수행한다. 키는 DGS·외부 구간에 두지 않는다. 3.3절 U1 방식에서 항우연은 키를 알 필요가 없다.
- **접근 통제**: 키 파일은 ROS 서비스 계정만 읽을 수 있게 하고, 사람 계정의 직접 열람을 막는다.
- **분실 대비**: 키 사본은 오프라인 봉인 보관(예: 암호화 USB 2개를 서로 다른 장소에 보관)하고, 꺼낼 때는 2인 입회와 기록을 남긴다. (8.4절)
- **사전 탑재**: 발사 전 위성에 탑재하는 키와 지상 보관 키가 일치하는지 통합 시험에서 확인한다.
- **인원 변경**: 키 보관 담당자가 바뀌면 인수인계 기록을 남기고, 가능하면 키를 교체한다.

## 5. [2] 명령 경로 보호

### 5.1 TC 생성·송출 점검 프로세스

TC는 "계획 → 작성 → 자동 검증 → 검토·승인 → 송출 준비 → 송출 → 확인 → 기록"의 8단계로 처리한다. 각 단계는 ROS·MPS에 로그로 남는다.

```
[1 계획] → [2 작성] → [3 자동 검증] → [4 검토·승인] → [5 송출 준비(Go/No-Go)] → [6 송출] → [7 확인] → [8 기록·종료]
   MPS        ROS         ROS            사람(위험도별)       패스 직전 브리핑         ROS→DGS     TM/ACK       로그
```

#### 단계별 내용

| 단계 | 수행 | 내용 | 산출 기록 |
|---|---|---|---|
| 1. 계획 | 임무계획 담당 | 임무 요청·궤도·패스 일정을 반영해 Mission Schedule 작성, 운용 책임자 확정 | 확정 스케줄(버전 번호) |
| 2. 작성 | 운용자 | 확정 스케줄에 따라 TC 목록 작성. **명령 DB에 정의된 명령만** 선택 가능 | TC 목록 초안 |
| 3. 자동 검증 | ROS | 아래 3.1~3.5 검사. 하나라도 실패하면 진행 불가 | 검증 결과 |
| 4. 검토·승인 | 위험도별 (5.2절) | 일반: 작성자 자기 확인 / 주의: 동료 확인 / 위험: 운용 책임자 승인 (작성자 ≠ 승인자) | 승인자·시각 |
| 5. 송출 준비 | 운용팀 | 패스 직전 Go/No-Go 체크리스트 (5.3절) | 체크리스트 결과 |
| 6. 송출 | ROS | 승인된 TC 목록에 HMAC 부착 → 프레임 구성 → DGS 연동 게이트웨이로 전달 | 송출 TC ID·HMAC 순번 |
| 7. 확인 | 운용자 | ACK·TM으로 수행 결과 확인. 미수신 시 재송출 여부 판단(재송출도 같은 절차) | ACK 결과 |
| 8. 기록·종료 | 운용자 | 패스 보고서 작성, 이상 사항 기록 | 패스 보고서 |

#### 자동 검증 항목 (3단계)

검증 로직은 **단순한 허용 목록 대조**로 구성한다.

1. **명령 존재 확인**: 명령 DB에 정의된 명령인가
2. **파라미터 범위**: 각 파라미터가 명령 DB에 정의된 최소·최대·허용값 안에 있는가
3. **스케줄 일치**: 확정된 Mission Schedule(해당 버전)에 포함된 명령인가
4. **시간창**: 확정된 패스 시간 안에 송출되는가
5. **상태 제약**: 명령 DB에 정의된 사전 조건(예: 특정 모드에서만 허용)을 최근 TM이 만족하는가

### 5.2 TC 위험도 분류

| 위험도 | 예시 | 승인 | 비고 |
|---|---|---|---|
| 일반 | 상태 조회, TM 요청, 일반 데이터 다운로드 요청 | 작성자 자기 확인 | 자동 검증 통과 시 송출 가능 |
| 주의 | 탑재체 모드 변경, 운용 파라미터 변경, 시각 동기 | 동료 1인 확인 | 확인자는 작성자와 다른 사람 |
| 위험 | 리셋, 시스템 모드 전환, SW·FPGA 업로드, 통신 설정 변경, 키 변경, 인증 설정 변경, 데이터 삭제 | 운용 책임자 승인 + 재인증 | 작성자 ≠ 승인자, 필요 시 FlatSat 사전 확인 |

위험도는 명령 DB에 명령별 속성으로 저장하며, 위험도 변경 자체도 운용 책임자 승인 대상이다.

### 5.3 패스 직전 Go/No-Go 체크리스트

| 항목 | 확인 내용 |
|---|---|
| 일정 | 항우연 패스 확정 일정과 우리 Contact Schedule 일치 |
| 연동 | VPN 연결·프레임 스트림 정상, 항우연 측 준비 완료 통보 |
| 위성 상태 | 직전 패스 TM에 이상 없음, 비정상 플래그 확인 |
| TC 목록 | 승인 완료, 스케줄 버전 일치 |
| 인원 | 운용자·(위험 TC 시) 승인자 대기 |
| 기록 | 로그 수집 정상 동작 |

### 5.4 비상 운용

LEO 패스는 약 10분 내외이므로 이상 상황에서 일반 절차를 다 밟기 어렵다. 보안 절차가 운용을 막으면 결국 우회가 생기므로, 다음을 **미리** 정한다.

- **사전 승인 비상 명령 세트**: 안전 모드 진입, 리셋 등 비상 대응 명령을 운용 책임자가 사전 승인해 두고, 비상 시 운용자 1인이 송출 가능하게 한다.
- **비상 송출 기록**: 비상 세트 사용 시 사유를 기록하고, 패스 직후 운용 책임자가 사후 검토한다.
- **비상 세트 외 명령**은 비상 시에도 일반 절차를 따른다.

### 5.5 항우연 연동 경계의 TC/TM 필터링: 필요성·효용성 판단

연동 경계에서 무엇을 막을지를 세 계층으로 나누어 판단하였다.

#### (1) 네트워크 방화벽 (L3/L4) — **필수**

- **내용**: VPN 터널 안에서도 항우연 상대 주소·약속된 포트만 허용하고, 그 외 모두 차단·기록한다. 연결 방향도 고정한다.
- **효용**: 항우연 측이 침해되었을 때 그쪽에서 우리 내부로 들어오는 경로를 최소화한다. 반대 방향도 막아 항우연에 대한 우리의 위험 전파를 줄인다. 항우연 협의에서도 가장 먼저 요구될 항목이다.
- **비용**: 낮음. 일반 방화벽·nftables 규칙 몇 줄로 구현된다.

#### (2) 송출 TC 게이트 (Uplink 내용 확인) — **권장 (단순 버전으로)**

- **문제**: HMAC은 ROS에서 계산된다. **ROS가 탈취되면 공격자도 올바른 HMAC을 붙일 수 있다.** 이 경우 위성은 정상 명령으로 받아들인다.
- **내용**: DGS 연동 게이트웨이에서 송출 직전 TC 프레임을 한 번 더 확인한다.
  - 형식 확인: 우리 위성 SCID·프레임 길이·구조
  - 시간창 확인: 확정된 패스 시간 안인가
  - 속도 제한: 패스당·분당 송출 수 상한
  - (선택) 승인 목록 대조: 승인 단계(5.1절 4단계)에서 확정된 TC 목록의 해시와 송출 프레임을 대조
- **효용**: ROS와 **다른 호스트**에서 동작하므로, ROS 단독 탈취로는 비인가 TC를 보낼 수 없게 하는 독립된 두 번째 확인이 된다. 다만 승인 목록 자체가 ROS에서 만들어지면 효과가 줄어들므로, 승인 목록 대조를 넣을 경우 승인 기록이 ROS를 거치지 않고 게이트로 전달되는 경로가 필요하다.
- **판단**: 형식·시간창·속도 제한은 로직이 단순하고 효과가 분명하므로 **적용**한다. 승인 목록 대조는 구현 복잡도가 있으므로 **2단계 구축 시 선택 적용**으로 둔다.
- **주의**: 상용 방화벽은 CCSDS·AX.25 프레임 내용을 해석하지 못하므로, 이 게이트는 DGS 연동 게이트웨이의 **자체 소프트웨어**로 구현한다. 규칙을 최소한으로 유지해 오탐으로 정상 TC가 막히지 않게 한다.

#### (3) 수신 TM 입력 검증 (Downlink 내용 확인) — **필수 (단, 격리 보관)**

- **문제**: 항우연 측이나 RF 구간에서 조작된 프레임이 들어오면, ROS의 TM 파서 취약점을 통해 내부 운용 영역이 공격받을 수 있다.
- **내용**: DGS 연동 게이트웨이에서 내부로 넘기기 전 프레임 길이·동기 패턴·CRC·SCID를 확인한다.
- **효용**: 내부 파서를 보호하는 입력 검증으로 효과가 크고 로직이 단순하다.
- **주의**: 검증에 실패한 프레임을 **버리지 않고 격리 보관**한다. 수신 품질이 나쁜 프레임도 위성 이상 분석에 필요할 수 있기 때문이다. 격리 프레임은 내부로 자동 전달하지 않고, 분석이 필요할 때 운용자가 별도로 가져간다.

#### 판단 요약

| 계층 | 판단 | 구현 위치 | 비용 |
|---|---|---|---|
| 네트워크 방화벽 (L3/L4) | 필수 | 경계 방화벽 | 낮음 |
| 송출 TC 게이트 (형식·시간창·속도) | 적용 | DGS 연동 게이트웨이 SW | 중간 |
| 송출 TC 게이트 (승인 목록 대조) | 선택 (2단계) | DGS 연동 게이트웨이 SW | 중간~높음 |
| 수신 TM 입력 검증 (격리 보관) | 필수 | DGS 연동 게이트웨이 SW | 낮음 |

## 6. [3] 데이터 무결성 검증 범위 정리

### 6.1 기존 계획서에서 말한 "파일 검증"의 의미

기존 검토에서 말한 파일 검증은 **위성 탑재 측 검증이 아니라, 지상국 내부로 들어오는 반입 단계의 검증**이었다.

프레임·패킷 단위의 HMAC과 CRC는 "이 데이터가 전송 중에 바뀌지 않았고, 우리 지상국이 보냈다"는 것을 증명한다. 이것만으로 **전송 구간** 무결성은 충분하다는 데 동의한다. 그러나 HMAC은 *ROS가 받은 파일이 올바른 파일인지*는 증명하지 못한다. 탑재체팀 계정이 탈취되거나 잘못된 버전이 전달되면, ROS는 그 파일에 HMAC을 정상적으로 붙이고 위성은 정상적으로 받아들인다.

즉 문제는 HMAC을 붙이기 **전**, 탑재체팀(SDC) → MOC로 파일이 들어오는 단계다.

### 6.2 구간별 검증 책임

| 구간 | 대상 | 검증 방식 | 결정 주체 | 상태 |
|---|---|---|---|---|
| ① 탑재체팀 → MOC (지상국 내부 반입) | SIREN 가중치, PL 비트스트림, 운용 파라미터, 실행파일 | 해시 확인 + 버전 관리 + 운용 책임자 승인 + (위험 업로드) FlatSat 시험 | **지상국팀** (본 과제 범위) | 설계 대상 |
| ② 경희대 ↔ 항우연 (지상 연동) | 프레임 스트림 | VPN 암호화·상호 인증 (U1 방식이면 추가 서명 불필요) | 양 기관 협의 | 3장 |
| ③ 지상국 → 위성 (RF 구간) | TC 프레임·패킷 | HMAC + CRC | 위성 개발팀 | 결정됨 (4장) |
| ④ 위성 내부 (파일 재조립 후) | 분할 업로드된 파일 전체 | 재조립 후 전체 해시 확인 | 위성 개발팀 | 협의 사항 (필수 아님) |

### 6.3 ① 지상국 내부 반입 검증 (본 과제 범위)

로직은 단순하게 유지한다.

1. 탑재체팀은 파일과 함께 **해시값과 버전 정보**를 제출한다. 해시값은 파일과 다른 경로(예: 메신저가 아닌 별도 승인 기록)로 전달한다.
2. DGS 교환 영역에서 해시를 다시 계산해 대조한다. 불일치 시 반입을 거부한다.
3. 운용 책임자가 버전·용도를 확인하고 승인한다.
4. SW·FPGA·실행파일 등 **위험 업로드는 FlatSat(또는 EM)에서 먼저 동작을 확인**한 뒤 승인한다.
5. 승인된 파일만 ROS 업로드 대기 목록에 들어가며, 이후 5.1절 TC 절차를 따른다.

전자서명 체계(탑재체팀 서명키 발급·관리)는 운영 부담에 비해 효과가 해시+승인과 크게 다르지 않으므로 **기본 적용하지 않고**, 탑재체팀이 원격으로 직접 제출하는 구조가 될 때 재검토한다.

### 6.4 TC 요청 문서 방식(U3)의 경우

항우연이 프레임 대신 **TC 요청 문서**를 받아 직접 TC를 만드는 방식으로 결정되면, ② 구간에서 문서 자체의 진위가 문제가 된다. 이때는 다음이 필요하다.

- 요청 문서에 **전자서명**(경희대 운용 책임자 키)을 붙이고, 항우연이 송출 전에 검증한다.
- 문서에 패스 ID·유효 시각·일련번호를 넣어 재사용을 막는다.
- 이 방식에서는 위성 HMAC 키를 항우연이 보유해야 하므로, 키 제공 범위와 보관 책임을 별도 협의해야 한다.

## 7. [4] 단일 접점 망분리 설계 (핵심)

### 7.1 설계 기본 구조

**DGS만 외부와 통신하고, 나머지 서브시스템(ROS·MPS·FDS·SDC)은 외부망과 완전히 분리한다.** 서브시스템과 외부 사이의 모든 데이터는 DGS를 거친다.

DGS 내부는 외부 상대에 따라 역할을 둘로 나눈다. 논리적으로는 모두 DGS이지만, **서로 다른 호스트(또는 VM)**로 구성한다.

- **DGS 연동 게이트웨이 (DGS-GS)**: 항우연·연세대 VPN 종단, 프레임 중계, 5.5절 TC 게이트·TM 입력 검증. **인터넷 연결 없음.**
- **DGS 인터넷 게이트웨이 (DGS-NET)**: Space-Track TLE 조회, 발사체 State Vector 수신. **TC 경로와 무관.**

이렇게 나누는 이유는 *인터넷 → DGS → 항우연 연동 회선* 경로를 구조적으로 없애기 위해서다. 인터넷에 연결된 호스트가 탈취되어도 TC 경로와 항우연 연동 회선에 직접 닿지 않는다.

### 7.2 구역 구성

| 구역 | 구성 요소 | 외부 연결 | 원칙 |
|---|---|---|---|
| Z0 외부 | 인터넷(Space-Track, 발사체 제공자), 항우연·연세대 VPN | - | 통제 불가 영역 |
| Z1 DGS 경계 | DGS-GS, DGS-NET | DGS-GS: VPN만 / DGS-NET: 인터넷 아웃바운드만 | 데이터 무저장(중계 후 삭제), 입력 검증 후 내부 전달 |
| Z2 운용 | ROS, MPS, FDS, DGS 내부(아카이브·카탈로그·교환 영역), 운용 단말 | **없음** | 인터넷 완전 차단, 등록된 운용 단말만 접속 |
| Z3 SDC | CDPS, SDPS (탑재체팀) | 학내망 (필요 시) | Z2와 직접 통신 금지, DGS 교환 영역만 경유 |
| Z4 관리 | 로그 서버, 백업 서버, 내부 업데이트 저장소, 내부 시각 서버, 관리 단말 | **없음** | 관리 접속 전용, 로그는 단방향 수신 |

```
                 인터넷                        항우연 / 연세대
                   │                              │ (IPsec VPN)
           ┌───────┴───────┐              ┌───────┴───────┐
   Z1      │   DGS-NET     │              │    DGS-GS     │   ← 서로 다른 호스트, 상호 통신 없음
           │ (TLE·SV 수신)  │              │ (프레임 중계)   │
           └───────┬───────┘              └───────┬───────┘
                   │ 검증된 TLE·SV               │ TM 프레임 ↓ / TC 프레임 ↑
   ════════════════╪══════════ 경계 방화벽 ═════════╪═══════════════════
                   │                              │
   Z2      ┌───────┴──────────────────────────────┴────────┐
 (운용)     │   FDS        MPS        ROS     DGS 내부        │
           │                              (아카이브·교환)    │
           └───────────────────────┬───────────────────────┘
                                   │ 교환 영역만 경유
   Z3                       ┌──────┴──────┐
  (SDC)                     │ CDPS · SDPS │
                            └─────────────┘
   Z4 (관리): 로그 서버 · 백업 서버 · 업데이트 저장소 · 시각 서버  ← 모든 구역에서 로그 단방향 수신
```

### 7.3 구현 방식

- **방화벽 1대 + VLAN 구역 분리**를 기본으로 한다. 계층형 방화벽 3대 구성은 학생 조직이 유지하기 어렵다.
- 각 호스트에 **호스트 방화벽**(nftables 등)으로 같은 허용 규칙을 한 번 더 적용한다. 경계 방화벽 설정 오류를 보완한다.
- DGS-GS와 DGS-NET은 **같은 VLAN에 두지 않는다.** 두 호스트 사이 통신 규칙은 존재하지 않는다.
- Z2·Z4는 인터넷에 나갈 수 없으므로 다음을 내부에 둔다.
  - **업데이트 저장소**: OS·패키지 업데이트를 관리 담당자가 외부에서 받아 검사 후 반입
  - **시각 서버**: GPS 수신기 기반 NTP. TC 시간창 검사와 로그 시각 정합의 기준
- 운용 단말은 Z2 전용 장비로 지정하고, 개인 노트북 접속과 이동식 매체 사용을 통제한다.

### 7.4 흐름 허용표

기존 N2 chart의 흐름을 단일 접점 구조로 다시 정리한 허용 목록이다. **이 표에 없는 통신은 모두 차단·기록한다.**

| ID | 출발지 → 목적지 | 데이터 | 방향·조건 |
|---|---|---|---|
| R01 | DGS-NET → Space-Track | TLE 조회 (HTTPS) | 내부 시작 연결만 |
| R02 | 발사체 제공자 → DGS-NET | State Vector File | LEOP 기간 한시 허용, 종료 후 규칙 삭제 |
| R03 | DGS-GS ↔ 항우연·연세대 | TM 프레임(↓), TC 프레임(↑), 운용 파일 | VPN 내부, 상대 주소·포트 고정 |
| R04 | DGS-NET → DGS 내부(교환 영역) | 검증된 TLE·State Vector | 형식·범위 검증 통과분만, 단방향 |
| R05 | DGS-GS → ROS | 검증된 TM 프레임 | 단방향 |
| R06 | DGS-GS → DGS 내부 | Payload Raw Data | 단방향 |
| R07 | ROS → DGS-GS | HMAC 부착 TC 프레임 | **TC 출발지는 ROS로만 한정** |
| R08 | FDS → DGS-GS | Antenna Pointing File, 패스 요청 | 파일 형식 검증 |
| R09 | Z2 서브시스템 간 | 운용 데이터 (N2 chart 내부 흐름) | 흐름별 개별 허용, 서비스 계정 |
| R10 | Z3 SDC ↔ DGS 내부 교환 영역 | Payload Raw Data(→SDC), Mission Request·Uplink 파일(→교환 영역) | SDC는 교환 영역만 접근, 6.3절 반입 검증 |
| R11 | 교환 영역 → MPS / ROS | 승인된 Mission Request / 승인된 Uplink 파일 | 운용 책임자 승인 후 |
| R12 | 전 구역 → Z4 로그 서버 | 로그 | 단방향 |
| R13 | Z2 → Z4 백업 서버 | 백업 데이터 | 백업 서버가 가져가는 방식(pull) 권장 |
| R14 | Z4 관리 단말 → 전 구역 | 원격 관리 (SSH) | 관리 단말에서만, 개인 계정 + MFA |
| R15 | 전 구역 → Z4 업데이트 저장소·시각 서버 | 패키지 다운로드, NTP | 읽기 전용 |
| R99 | 그 외 전부 | - | **차단 및 기록** |

※ 포트·프로토콜은 구축 단계에서 확정한다.

R06의 화살표는 **데이터 방향**이다. DMZ에서 운용 VLAN으로 새 연결을 시작하지 않도록 DGS-Archive가 DGS-GS의 읽기 전용 SFTP 서비스(개발방향 F19)에 접속해 원시데이터를 회수한다. 구체적인 임시 보관 용량·시간은 TBD(ICD)이다.

### 7.5 계정·권한

| 역할 | 권한 | 제한 |
|---|---|---|
| 운용자 | TC 작성, 일반·주의 TC 송출, TM 조회 | 위험 TC 승인 불가 |
| 운용 책임자 | 위험 TC 승인, 스케줄 확정, 파일 반입 승인 | 자신이 작성한 위험 TC 승인 불가 |
| 임무계획 담당 | 스케줄 작성 | 확정 불가 |
| 비행역학 담당 | 궤도 산출 | TC 권한 없음 |
| 탑재체팀 | 교환 영역 업로드·다운로드 | Z2 접근 불가 |
| 시스템 관리자 | OS·인프라 관리 | **TC 송출·승인 권한 없음** |
| 키 보관 담당 | HMAC 키 사본 관리 (2인) | 단독 열람 불가 |

- 공용 계정을 금지하고 개인 계정을 사용한다.
- 인원 이탈·역할 변경 시 즉시 권한을 회수하고, 학기 시작마다 전체 권한을 재검토한다(학생 조직 특성상 학기 단위가 실질적).

### 7.6 학교 측 협의 사항

- 정보처: VPN용 고정 공인 주소, 학내망 방화벽 정책 예외, (향후) 전용회선 개설
- 시설: MOC 공간 출입 통제, 서버 랙 잠금, 전원(UPS)

## 8. [5] 로그·백업 체계 (필수)

### 8.1 목표

1. **TC 추적성**: 어떤 TC든 "누가 계획하고, 누가 작성하고, 누가 승인하고, 언제 송출했고, 위성이 어떻게 응답했는지"를 재구성할 수 있다.
2. **사고 분석**: 침해·장애 발생 시 경로를 추적할 수 있다.
3. **복구 가능성**: 어떤 서버를 잃어도 정해진 시간 안에 운용을 재개할 수 있다.
4. **항우연 협의 대응**: 사고 시 상대 기관에 제공할 근거를 확보한다.

### 8.2 로그 설계

#### 수집 대상

| 분류 | 이벤트 | 발생 위치 |
|---|---|---|
| TC 생애주기 | 계획 확정, 작성, 자동 검증 결과, 승인/거부, 송출, ACK, 비상 세트 사용 | MPS, ROS |
| TC 게이트 | 송출 허용/차단, 차단 사유(형식·시간창·속도) | DGS-GS |
| TM 수신 | 패스별 수신 프레임 수, 검증 실패·격리 프레임 수, HMAC 실패 카운트(위성 TM) | DGS-GS, ROS |
| 연동 | VPN 연결·해제, 인증 실패, 상대 주소 이상 | DGS-GS, 경계 방화벽 |
| 파일 반입 | 업로드, 해시 대조 결과, 승인, 반입 거부 | DGS 교환 영역 |
| 인증·권한 | 로그인 성공·실패, MFA 실패, 권한 변경, 계정 생성·삭제 | 전 구역 |
| 네트워크 | 방화벽 차단 기록 (특히 R99) | 경계·호스트 방화벽 |
| 설정 변경 | 명령 DB·위험도 변경, 방화벽 규칙 변경, 키 접근 | 전 구역 |

#### 로그 형식

모든 로그는 같은 기본 필드를 갖는 **한 줄 JSON**으로 기록한다. 검색·대조 로직을 단순하게 유지하기 위해서다.

```json
{"ts":"2026-11-20T03:14:15.123Z","host":"ros01","zone":"Z2","event":"tc.approve",
 "user":"kim.operator","pass_id":"P-20261120-01","tc_id":"TC-000412",
 "risk":"high","result":"ok","detail":"approved by lee.lead"}
```

- `ts`는 UTC, 내부 시각 서버 기준
- `pass_id`, `tc_id`로 패스·명령 단위 추적

#### 수집·보호

- 각 호스트는 로그를 Z4 로그 서버로 **단방향 전송**한다. 로그 서버에서 다른 구역으로 나가는 연결은 없다.
- 로그 서버는 **추가 전용**(append-only)으로 운영하고, 일 단위로 로그 파일의 해시를 기록해 사후 변조를 확인할 수 있게 한다.
- 로그 서버 관리자와 운용 책임자는 다른 사람으로 지정한다.

#### 보관 기간

| 로그 | 보관 기간 |
|---|---|
| TC 생애주기, TC 게이트, 키 접근, 설정 변경 | **임무 종료 시까지** (영구 보관) |
| 인증·권한, 연동, 파일 반입 | 임무 종료 + 1년 |
| 네트워크 차단 기록 | 1년 |

※ 항우연 협의 결과 보관 요구가 있으면 그에 맞춘다.

#### 점검

| 주기 | 점검 내용 |
|---|---|
| 매 패스 후 | 송출 TC와 승인 기록 대조, TC 게이트 차단 여부, HMAC 실패 카운트 |
| 주 1회 | 인증 실패, R99 차단 기록, 비상 세트 사용 내역 |
| 월 1회 | 설정 변경 이력, 로그 해시 대조 |

전용 SIEM은 초기에 도입하지 않는다. 위 점검을 **스크립트 몇 개**(필드 기준 검색·집계)로 수행하고, 운용 규모가 커지면 재검토한다.

### 8.3 백업 설계

#### 백업 대상과 목표

| 대상 | 중요도 | 백업 주기 | 복구 목표 |
|---|---|---|---|
| HMAC 키 | 최상 (분실 시 위성 제어 불가) | 변경 시 | 즉시 (8.4절 별도 관리) |
| 명령 DB (명령 정의·위험도·파라미터 범위) | 최상 | 변경 시 + 일 1회 | 다음 패스 전 |
| ROS·MPS·FDS 설정 및 SW | 상 | 변경 시 + 주 1회 | 24시간 이내 |
| 확정 스케줄, 송출 TC 기록 | 상 | 패스 후 | 다음 패스 전 |
| TM·Payload 원시 데이터 | 상 | 패스 후 | 24시간 이내 (분석용) |
| FDS 궤도 산출물 | 중 | 일 1회 | 재계산 가능 |
| 로그 | 상 | 일 1회 | 72시간 이내 |
| 방화벽·VPN 설정 | 상 | 변경 시 | 24시간 이내 |

#### 3-2-1 원칙 적용

- **사본 3개**: 원본 + Z4 백업 서버 + 오프라인 매체
- **매체 2종**: 백업 서버 디스크 + 오프라인 외장 디스크(또는 테이프)
- **오프라인 1개**: 주 1회 오프라인 매체에 복사 후 분리 보관 (MOC 외부 장소)

#### 백업 보호

- 백업 서버가 각 호스트에서 데이터를 **가져가는(pull)** 방식으로, 운용 호스트가 탈취되어도 백업을 지울 수 없게 한다.
- 백업 저장소는 일정 기간 수정·삭제가 불가능한 방식(불변 스냅샷 등)으로 운영한다.
- 백업 데이터는 암호화하고, 암호화 키는 백업과 분리 보관한다.

#### 복구 시험

| 주기 | 시험 내용 |
|---|---|
| 학기 1회 | ROS 서버 1대를 백업만으로 재구축해 FlatSat 대상 TC 송출까지 확인 |
| 학기 1회 | 오프라인 매체에서 명령 DB·로그 복원 확인 |
| 발사 전 1회 | 전체 운용 영역 재구축 시험 (소요 시간 측정) |

### 8.4 HMAC 키 백업 (별도 관리)

- 키 사본 2개를 암호화된 매체에 담아 **서로 다른 장소**에 봉인 보관한다.
- 꺼낼 때는 **2인 입회**, 사유·일시·입회자를 기록한다.
- 봉인 상태를 학기마다 확인하고 기록한다.
- 키 교체 시 기존 사본을 폐기하고 폐기 기록을 남긴다.

## 부록 A. N²SF 통제 영역 대응표 (참조용)

항우연이 N²SF 기준의 설명을 요구할 경우를 대비한 대응표다. 본 설계의 등급은 N²SF 등급(C/S/O)이 아니라 **자체 영향도 구분**(명령 경로 / 운용 / 공개)을 사용한다.

| N²SF 통제 영역 | 본 설계의 대책 | 해당 절 |
|---|---|---|
| 권한 | 역할별 권한, 직무 분리, 위험 TC 승인 | 5.2, 7.5 |
| 인증 | 개인 계정 + MFA, VPN 인증서 상호 인증, 위성 TC HMAC | 3.4, 4, 7.5 |
| 분리 및 격리 | 단일 접점 구역 분리, DGS-GS / DGS-NET 분리 | 7.1~7.3 |
| 통제 | 흐름 허용표, TC 게이트, TM 입력 검증 | 5.5, 7.4 |
| 데이터 | 반입 해시 검증, 백업 암호화·불변 보관 | 6.3, 8.3 |
| 정보자산 | 등록 운용 단말, 내부 업데이트 저장소, 로그 수집 | 7.3, 8.2 |
