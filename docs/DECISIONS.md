## #16 운영 배포를 단일 VM·서브시스템별 Docker로 변경

- 날짜: 2026-10-23
- 배경: 사용자가 실제 운영도 Linux VM 한 대에서 Docker 컨테이너를 나누어 수행한다고 확정했다. 기존 개발방향의 VM 8대·VLAN별 방화벽·vm-mgmt 별도 VM은 실제 구축 구조와 맞지 않는다.
- 결정: 호스트 UFW는 VM 자체로 들어오는 트래픽을 제한하고, Docker의 내부 전용 브리지로 서브시스템 간 연결 쌍을 나눈다. 웹 UI 완성 전 공개 컨테이너 포트는 0개다. N2 연결 방향과 상대 신원은 실제 서비스 리스너·mTLS·SFTP 권한에서 따로 강제한다. 시간 동기는 VM 호스트를 사용하고 컨테이너 로그는 호스트 journald로 수집한다.
- 근거: Docker 문서는 공개 컨테이너 포트가 UFW 입력 규칙을 우회할 수 있다고 명시한다. 내부 전용 사용자 브리지는 공유하지 않는 컨테이너 쌍의 네트워크를 분리하지만, 같은 브리지 안에서 연결 시작 방향까지 제한하지 않는다.
- 영향: 이전 VM·VLAN·nftables 배포 조항은 대체한다. 단일 VM의 Docker 관리자와 호스트가 모든 서브시스템에 영향을 줄 수 있으므로 VM별 장애·침해 격리라는 이전 가정은 성립하지 않는다. 단계 7 probe는 배포 기반 검증이며 운용 서비스 배포 완료를 뜻하지 않는다. 외부 ICD·관리 PC·스토리지 연결은 확정 뒤 별도 승인 흐름으로 활성화한다.

## #8 단계 2 공통 전송 계약

- 날짜: 2026-10-21
- 배경: 개발방향 9.1절은 길이 접두 TCP/TLS, SFTP 파일·매니페스트, VM 내부 Unix socket을 지정하지만, 프레임 크기·파일 공개 순서·호스트 키 확인 형식은 구현 계약으로 정해져 있지 않다.
- 결정: 실시간 TLS 프레임은 4바이트 네트워크 바이트 순서 길이와 최대 1 MiB, Unix socket JSON 프레임은 같은 접두 형식과 최대 64 KiB로 제한한다. TLS는 양쪽 인증서와 상대 VM IP의 SAN을 검증한다. SFTP는 SSH 서버 공개키의 SHA-256 해시를 고정하고 공개 파일명 `<data>.manifest.json`을 사용한다. 업로드는 데이터 파일을 먼저, 매니페스트를 마지막에 공개한다. 다운로드는 매니페스트의 경로·유형·해시 확인 뒤 로컬 파일을 공개한다.
- 이유: 외부 입력의 최대 크기를 제한하고, 미완료 파일이 수신처에서 처리되지 않게 하며, VM 통신 상대를 검증하기 위함이다.
- 영향: Linux에서 OpenSSL과 개발방향 11.1절의 libssh가 필요하다. 키·인증서는 실행 시 파일 경로로만 지정하고 저장소에 두지 않는다. 실제 VM의 IP·계정·호스트 키 값은 장비 확정 후 설정한다.

- 영향: 4-1에는 시퀀스 출력·승인·TC 송출·웹 API가 없다. `operational: false` DB는 표시 가능한 빈 목록일 뿐 운용 명령으로 사용되지 않는다. 외부 입력 파서는 비정상 입력 단위 시험과 퍼징 대상을 둔다.

## #12 단계 4-2·4-3 비운용 계획·분석 계약

- 날짜: 2026-10-21
- 배경: 실제 TC 명령 속성, FDS 파일 형식과 전송률·패스당 명령 상한이 아직 확정되지 않았다. 사용자가 4-2와 4-3을 함께 진행하도록 요청했다.
- 결정: MPS 초안의 패스 전체 시간창과 현 비운용 명령 DB 정수 버전을 결합하고, 한 프로세스의 제한된 불변 리비전 이력과 기대 리비전 기반 수정 거부를 구현한다. 충돌 6개 규칙은 `interfaces/mps/test_contract.md`의 합성 속성과 명시적 시험 프로파일로만 분석한다.
- 영향: 임의의 TC 명령 항목을 운용 DB에 넣지 않는다. 합성 분석 통과는 승인 조건이 아니며, 현재 코드에는 영속 저장소, 파일 출력, ROS 연결, TC 송출 경로가 없다. 실제 명령 DB 해시·속성 및 FDS 입력·계획 저장 정책은 후속 계약이 정해진 뒤 연결한다.

## #13 단계 4-4·4-5 비운용 승인·반입 경계
